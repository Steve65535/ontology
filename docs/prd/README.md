# Autelogy 本体论平台 PRD

状态：产品基线草案。本文从技术笔记提炼产品目标、详细需求与验收口径，实际交付状态须结合应用代码验证。架构实现见[总体架构](../architecture/README.md)，重点机制见[编译器](../architecture/compiler.md)、[执行器](../architecture/executor.md)、[Function](../architecture/functions.md)和[语言关键字](../architecture/keywords.md)。

## 1. 产品定位

Autelogy 面向需要让人和 Agent 共同处理业务的组织，提供一套可执行的业务本体：定义业务中有什么对象、对象之间如何关联、允许执行哪些操作、必须遵守什么规则，以及每次操作由谁发起、造成什么结果。

平台将本体定义转化为查询能力、受控业务操作、数据校验和 Agent 工具。业务含义与执行规则保持同源，减少在数据库、业务接口和 Agent 工具之间重复维护逻辑。

## 2. 用户与问题

| 用户 | 当前问题 | 期望结果 |
| --- | --- | --- |
| 业务建模者 | 表结构不能完整表达业务含义、关系名称和操作规则 | 用统一模型描述业务，保存前发现定义错误 |
| 业务操作人员 | 不清楚操作会影响哪些对象，失败后难以判断原因 | 查看影响、执行合法操作、理解拒绝原因 |
| Agent 开发者 | 每接一个业务都要手写工具和规则说明 | 从本体获得工具、限制和可执行的错误反馈 |
| 管理与审计人员 | 自动化操作责任不清，变更缺少完整上下文 | 控制权限与风险，追溯发起人、授权人和因果链 |
| 平台集成团队 | 既有数据库接入成本高，结构变化容易破坏模型 | 接入现有数据或创建托管数据，并识别结构漂移 |

## 3. 产品目标与范围

### 3.1 核心目标

- 让业务知识成为统一、可检查、可执行的模型。
- 让人、应用和 Agent 使用一致的业务操作及约束。
- 让写入具有明确权限、可预演的影响和可追溯的结果。
- 支持从既有 PostgreSQL 数据起步，也支持按模型建立托管数据结构。

### 3.2 范围边界

基线以 PostgreSQL 业务数据、单数据源内的事务执行和 HTTP／MCP 接入为中心。首阶段产品交付应优先跑通一个业务域的建模、查询、操作与审计闭环。

跨数据库原子事务、任意 SQL 写入、完整 ETL、通用工作流设计器和自主 Agent 规划不属于本版范围。非 SQL 事实源已有模型声明思路，连接协议与运行时接入须另行确认；不得据此承诺已支持时序库、消息队列或设备协议。

## 4. 核心产品概念

| 概念 | 含义 | 采购业务示例 |
| --- | --- | --- |
| `ObjectType` | 一类具有稳定身份的业务对象 | 采购订单、供应商 |
| `PropertyType` | 对象或关系的属性，可来自存储列或计算结果 | 订单金额、状态 |
| `LinkType` | 具有名称、方向和基数的业务关系 | 订单属于供应商 |
| `ActionType` | 具有参数、权限、前置条件和副作用的业务操作 | 提交订单、审批订单 |
| `Constraint` | 值域、状态、关系或操作必须遵守的规则 | 金额范围、合法审批状态迁移 |
| `Function` | 不改变业务状态的计算或读取 | 计算订单汇总值 |
| `Interface` | 多类对象共享的属性、关系及操作契约 | 多种单据统一实现“可审批”接口 |

`Workspace` 组织模型与治理的工作空间，`Domain` 划分业务领域，`Datasource` 定义数据来源。`Actor` 表示执行者及其责任归属；`Datasource` 和 `Actor` 不属于七原语。

## 5. 关键用户流程

### 5.1 接入与建模

1. 集成团队配置数据源；连接凭据通过部署环境提供。
2. 建模者扫描既有数据库，或定义新的托管对象。
3. 确认主键、展示属性、字段含义和关系名称，处理不支持的类型。
4. 补充操作、约束、角色要求及风险属性，通过模型校验后保存。
5. 托管对象先查看结构变更计划，再施加数据库变更；既有数据源保留结构基线供后续比对。

自动起草结果应作为草案交给建模者修订。系统不能替用户猜测业务身份、悄悄转换不兼容类型，或静默遗漏无法接入的字段与关系。

### 5.2 查询与操作

用户或 Agent 先通过 `describe` 理解模型，通过 `query` 获取对象及关系，再通过 `apply` 执行业务操作，最后通过 `events` 查看结果与因果关系。

以审批采购订单为例：先查询订单当前状态，选择审批操作并填写参数；执行时检查角色、数据范围和状态规则；成功后同步形成业务变更与审计记录，失败时返回具体原因。批量或级联操作应先展示预演结果，需确认的操作进入人工确认流程。

### 5.3 Agent 受控执行

Agent 从模型获得可用工具、参数、前置条件及副作用说明。服务端对每次调用重新执行权限和策略检查；是否出现在工具列表中不能替代授权。

对需要人工确认的操作，平台展示真实预演结果并将确认绑定到本次操作、参数、会话及变更结果。执行时发现影响已经变化，应要求重新预演和确认。

### 5.4 持续治理

管理者按对象、操作或会话查看审计记录，区分成功、拒绝和外部调用失败。结构漂移提示数据库与模型的不一致；约束漂移提示现存数据不再满足业务规则。扫描未覆盖的部分必须可见，由负责人决定修订模型还是治理数据。

## 6. 功能需求与验收

以下为产品要求，基于笔记中的能力整理，不代表已完成全部界面与集成。

| 编号 | 能力 | 核心要求 | 验收口径 |
| --- | --- | --- | --- |
| `PRD-01` | 本体建模 | 管理七原语，保存前检查引用、类型、关系及调用环 | 非法模型不能保存，错误能定位到具体定义 |
| `PRD-02` | 数据接入 | 扫描 PostgreSQL，起草对象与关系，支持托管建表 | 未处理的类型及命名问题明确列出；建表必须先看计划 |
| `PRD-03` | 数据查询 | 提供过滤、排序、分页、关系展开和接口查询 | 返回稳定分页及明确限制；超出支持范围时解释原因 |
| `PRD-04` | 业务操作 | 统一执行操作、约束和级联，支持 `dryRun` | 任一阻断规则失败，整条业务链回滚；预演不提交业务和审计写入 |
| `PRD-05` | Agent 工具 | 从本体生成工具与规则说明 | 无法放入参数 schema 的约束仍可被调用方看到；编译问题可见 |
| `PRD-06` | 权限与确认 | 角色、对象范围、密钥范围和风险策略共同生效 | 直接 HTTP 调用及接口级操作同样受控；过期影响不能复用确认 |
| `PRD-07` | 审计与会话 | 记录执行身份、代理责任、模型版本及因果链 | 能从一次操作追到对象变化、级联操作及关联会话 |
| `PRD-08` | 模型演进 | 保存版本与变更记录，管理结构计划 | 模型保存与 DDL 施加的状态分别可见，不能混淆 |
| `PRD-09` | 漂移治理 | 检查结构变化及现存数据的规则违反 | 区分发现、跳过与未完成范围，不把未检查解释为合规 |
| `PRD-10` | Function 计算 | 定义可复用的纯计算与只读计算，受控运行表达式和脚本 | 参数类型合法，纯度边界生效，故障不能被当作规则通过 |
| `PRD-11` | 语言与编译反馈 | 使用平台 DSL 编辑操作、规则、关系和接口 | 关键字补全、作用域诊断与格式化保持业务语义 |
| `PRD-12` | 批量与级联 | 支持有界批处理和子操作协作 | 全链权限、影响计数和事务一致，超限有明确反馈 |

### 6.1 风险与权限口径

| 情况 | 产品要求 |
| --- | --- |
| 可逆、单对象、无外部副作用 | 非人类执行者通过授权及自动化策略后可执行 |
| 批量或级联影响 | 展示风险与影响范围，建议先预演；会话累计影响也纳入治理 |
| 不可逆或具有外部副作用 | 非人类执行者必须取得人工确认 |
| `automatable: false` | 非人类执行者不能通过工具或直接调用绕过限制 |

人工确认不能代替业务权限。涉及资金等业务含义，需要建模者正确设置风险并配置规则，平台不会仅凭操作名称识别风险。

### 6.2 交互要求

产品应覆盖数据接入、模型编辑、对象查询、操作预演、待确认任务和审计查看。具体页面布局、可视化编辑深度及发布交互待设计确认。

失败反馈应区分“违反业务规则”“触及执行护栏”“引擎故障”，给出相应的下一步；不应引导 Agent 反复修改参数重试不可恢复的错误。

### 6.3 本体建模：`PRD-01`

建模者应能从业务概念出发定义七原语，并查看某个对象有哪些属性、关系、操作、规则和接口。编辑入口可以是结构化定义或 DSL，两者应收敛为相同模型。

具体要求：

1. 对象必须有稳定身份与展示属性；属性名、物理列名和中文业务说明分别表达，不能要求三者相同。
2. 属性区分存储列、派生值和聚合值，查询与编辑交互显示其可写性。金额、枚举、时间和对象引用等类型保留业务语义。
3. 关系声明两端对象、业务角色、基数和实现方式；不能只展示外键名称而让用户猜关系含义。
4. 操作同时定义参数、前置条件、步骤、角色要求、自动化属性及风险，能够查看关联规则。
5. 接口用显式映射连接共享属性与具体属性，不强迫已有对象为实现接口改名。存在多个实现者时才体现统一查询与操作的价值。
6. 保存前检查重复名称、悬空引用、表达式类型、接口映射与循环依赖。整个保存不合法时，不留下部分实体变更。

验收：将订单金额与文本比较、删除仍被操作引用的属性、使用不存在的关系或制造调用环，均应得到能定位的诊断。修正后保存成功，并能通过模型描述读取相同业务含义。

### 6.4 数据接入：`PRD-02`

集成团队可以接入已有 PostgreSQL 结构，也可以从模型创建托管结构。配置必须显示数据源管理模式、数据通道和引擎允许的能力，不能让“已连接”被误解为“可写”。

已有库接入流程应展示表、列、主键、外键和类型映射结果。建模者明确选择暴露字段、对象标识、展示属性及关系名称；无法映射的字段给出原因和允许的处理选项，不静默转换为字符串。

缺少主键时要求用户显式指定可用身份；主键类型无法进入模型时，拒绝生成无身份对象。原始列名不符合业务命名规则时，通过 binding 保留映射，让用户确认稳定的业务名称。

托管结构先保存模型，再展示 DDL 计划、影响范围和未下推规则，确认后施加。新增表或列不应与删除列、改类型等破坏性操作混在同一自动流程中。

验收：未处理的字段和关系有完整清单；起草结果保持草案状态；用户确认前不写业务表；计划变化后不能继续施加旧计划。`facts` 数据的模型声明与真实连接能力分别展示。

### 6.5 查询与浏览：`PRD-03`

用户可以按业务对象浏览数据、选择属性、过滤、排序和分页，并沿已定义关系查看相关对象。返回数据使用业务属性名，不要求调用方理解物理列名。

具体要求：

1. 分页排序有稳定规则，返回总数时，计数条件与数据条件一致。
2. 可选关系不存在时显示为空，不丢失整个父对象；多值关系展开不能改变父对象分页的含义。
3. 展开达到扇出或深度限制时，明确报告限制与截断信息，不把未返回解释为空关系。
4. 派生与聚合属性显示计算含义及只读状态；超出 SQL 下推范围的表达式明确拒绝。
5. 接口查询返回共享属性，并能识别具体对象类型；当前基线不承诺接口查询中的游标与关系展开。
6. 拒绝跨数据源关系展开及不支持的分页组合。读取权限和敏感属性覆盖须专门验收，不从写权限机制推导读取隔离已完善。

验收：包含相同排序值、空关系和多个子对象的数据集，在受支持的稳定数据场景中分页无重复、无漏项；错误组合返回说明，不产生看似完整的部分结果。

### 6.6 操作、预演与执行结果：`PRD-04`

用户从对象可用操作中选择业务动作并填写参数。操作界面应展示用途、角色要求、前置条件、风险及可能的关联影响，派生属性不能作为普通字段直接修改。

预演必须运行与正式执行相同的业务规则，展示对象新增、修改、删除及关系变化，以及警告和调用影响。预演完成后不提交业务变化、执行事件和幂等结果；外部调用不发送，也不伪造其返回结果。

正式执行时重新检查状态和授权，任一阻断规则不通过则整条业务链回滚。warning 应保留在结果中，与阻断原因明确分开；失败结果给出规则、字段路径或状态、可操作建议。

客户端重试应能使用幂等机制取得原成功结果，避免网络重试重复审批或创建记录。同键并发与键冲突行为需以实际接口契约和集成测试确认。

验收：一次操作先修改订单再触发子操作失败时，订单与子操作均不生效；预演与正式执行之间数据变化时，旧的预演不能被解释为最终结果；客户端不能只凭超时判定操作未发生。

### 6.7 Function 定义与运行：`PRD-10`

建模者应能定义具有业务名称、说明、参数和返回类型的计算，并在受支持的表达式和规则中引用。Function 的产品价值是复用业务计算，不承担写入操作。

| 能力 | 产品要求 |
| --- | --- |
| 表达式实现 | 使用受支持的表达式计算，保存时检查引用和类型 |
| 脚本实现 | 在隔离环境中计算，运行时间和内存受限制 |
| `pure` | 不具有本体查询能力，不能通过脚本拿到查询连接 |
| `readonly` | 通过受控的结构化查询读取数据，不具有业务写入能力 |
| 确定性与缓存声明 | 不能为非确定性计算声明可缓存；缓存实际范围另行核实 |
| 实现状态 | 明确表达式、脚本、`query`、`external` 的支持程度，不将可声明等同为可运行 |

参数错误应尽早定位。运行超时、脚本异常、读取失败和不支持的实现必须作为计算故障呈现；如果 Function 参与阻断规则，这类故障应使操作失败并回滚，不能默认返回“通过”。

是否提供独立 Function 调试页、通用调用 API 和 Agent 只读工具属于待确认交付入口。底层计算能力与这些入口的交付状态应分别描述。

验收：`pure` 脚本无法访问 `query`；`readonly` 无法写入；超时脚本能结束而不永久占住业务执行；同一计算用于规则时，业务判断不满足与计算运行故障显示不同原因。

### 6.8 语言关键字与编译反馈：`PRD-11`

平台自己的语言需要让建模者直接表达操作、约束、关系和接口。产品应提供关键字索引、上下文示例及编译诊断，让用户知道一个词在什么位置合法、改变哪部分业务语义。

Action 的已知词汇包括 `modify`、`as`、`display`、`roles`、`emits`、`idempotent`、`automatable`、`risk`、`require`、`else`、`hint`、`set`、`create`、`link`、`call_action`、`emit` 和 `for`。分类、用法与证据范围见[语言关键字](../architecture/keywords.md)，不将底层 effect 名称自动列为文本关键字。

具体要求：

1. 补全依据当前 DSL、语法位置、模型和作用域，区分语句关键字、内置函数、类型、业务名称与局部绑定。
2. 输入 `target.` 时建议当前对象合法成员；字段拼错或参数类型错误时给出定位和可用建议。
3. 步骤结果只能在创建之后引用，循环变量不泄漏到外部；不允许的嵌套循环或外部调用被明确拒绝。
4. 一行语法错误不妨碍其余行诊断；输入到一半仍尽量提供补全，但错误文本不能保存为有效模型。
5. 标准实体格式化为 DSL 后再次解析，保留参数、角色、风险、自动化和无环等关键语义。
6. 编译反馈区分语法错误、局部作用域错误与完整模型引用错误。用户修正前不能进入正式执行。

验收：编辑后未改变语义的往返保存，不会自动改变 `automatable` 或风险；未知词与非法名字有明确诊断；Constraint、Link、Interface 的完整关键字表由真实解析器核实后补全。

### 6.9 Agent 工具：`PRD-05`

Agent 可以从模型描述和工具集理解对象、业务操作、参数、前置条件及副作用，按业务目标选择操作。工具说明应使用可理解的业务语言，并包含可能的级联影响。

无法编码进工具输入 schema 的规则，通过未编码约束列表与说明暴露。工具编译失败或不暴露某个操作时，结果中要给出原因，不能仅记录日志后让调用方误认工具集完整。

`automatable: false` 的操作不应成为可执行自动化入口；即使 Agent 从描述中得知名称并直接调用 HTTP，服务端也要执行相同限制。工具展示出的风险和执行时的风险裁决应来自一致规则。

验收：Agent 能从描述回答“为什么能做、什么时候会被拒、可能影响什么”；遇到拒绝能区分调整参数、重新确认和联系维护者，不能原样无限重试。批量与外部调用的工具摘要覆盖须结合代码核实。

### 6.10 权限、身份与人工确认：`PRD-06`

管理者管理执行账户、密钥、角色和范围。业务角色授权与平台身份管理权限分别处理；人工审批者不能通过确认授予自己原本没有的业务权限。

每次执行检查角色、对象范围和密钥范围，级联子操作复用责任上下文并继续受控。非人类执行者按要求关联责任主体，会话身份由服务端签发和核实，不能相信客户端自报。

需要确认时，审批者查看具体对象、前后值、级联影响和外部副作用，再批准或拒绝。确认绑定会话、操作、参数和预演变化；替换目标、修改参数或实际影响改变时不能复用。笔记中的令牌消费失败边界意味着执行失败后可能需要重新确认。

验收：直接调用、接口级操作和工具调用不能绕过自动化策略；撤销或缺失权限后按实际身份契约拒绝；旧确认不能批准另一组变化。账户与密钥管理应留出可追踪的管理记录，具体界面与身份集成另行确认。

### 6.11 审计与会话：`PRD-07`

审计人员可以按对象、操作、执行者、会话和时间查看记录，并追踪一次操作引起的对象变化与子操作。记录包含模型版本，使历史结果能够关联到当时使用的定义。

结果区分业务成功、业务拒绝、规则警告和提交后的外部调用失败。业务已提交但通知失败时，界面不能显示为“订单没有审批成功”，也不能引导用户重新执行整笔业务。

事件追加保存，修正通过补偿事件表达。会话聚合显示相关操作与累计影响，帮助发现分多次完成的大规模修改。近期事件列表与可恢复订阅应按接口支持分别展示。

验收：能从一次审批定位发起人、责任主体、模型版本、订单变化和下游调用；断线重连按支持的订阅机制继续读取，不能把未完成订阅当作无事件。拒绝留痕失败需要运维可见，不能宣称失败审计绝不丢失。

### 6.12 模型版本与结构演进：`PRD-08`

建模者查看模型版本及变更前后内容，了解一个修改影响了哪些引用。校验失败时保留原模型和版本；删除被引用实体时列出阻塞引用。

模型保存和数据库结构施加分别呈现：保存了属性定义不表示物理列已经建立，DDL 成功也不能代替完整模型校验。迁移计划应列出实际步骤、未下推的规则和阻断原因，施加结果进入独立历史。

验收：确认计划后目标结构变化，旧指纹不能继续执行；迁移任一步失败不留下半份结构变更；有模型撤销能力时也必须重新校验依赖，不将它描述为自动回滚业务数据或任意数据库结构。

### 6.13 漂移发现与处理：`PRD-09`

结构扫描识别表、列、主键、类型及相关可空性变化，区分影响既有模型的变化与新增变化。扫描报告说明比较基线和检查范围，不能仅凭迁移计划为空判断结构完全一致。

约束漂移针对当前存量数据执行可适用规则，列出对象、违反规则、严重度及原因。需要真实变更镜像、无法计算或未覆盖的数据应列为跳过或未完成，不推断为合规。

负责人可以调查发现并决定修订模型、修正数据或接受记录。接受发现属于治理处理，不等于修改数据或证明规则已满足。

验收：外部库删除已建模字段后出现可定位发现；扫描被中断时保留部分完成标记；修改模型后出现的新违反不被静默覆盖。扫描频率、调度与通知渠道属于部署和产品决策。

### 6.14 批量与级联：`PRD-12`

批处理通过受限 `for_each` 或声明的子操作完成。用户应先了解目标数量及可预演的影响，不需要直接调用底层数据库进行批量修改。

全链共享事务、权限上下文、级联深度与累计影响计数。不能通过拆成多层调用或接口分派绕开护栏；会话策略还应考虑多次调用的累计影响。跨数据源级联写入不在本版承诺范围。

验收：任一批次项触发阻断，整次 Action 不留下部分业务结果；超过输入上限明确要求缩小范围，循环或过深调用提示检查模型。若未来需要逐项成功的任务，应定义独立异步任务产品语义，不能暗中改变当前全链回滚约定。

## 7. 产品工作区与主要交互

以下是建议的信息架构，用于组织交付，不代表当前前端已经具备全部页面。

| 工作区 | 核心内容 | 关键交互与状态 |
| --- | --- | --- |
| 数据接入 | 数据源能力、扫描结果、类型映射、结构基线 | 连接失败、待用户处理、草案就绪、结构漂移 |
| 本体建模 | 七原语、引用关系、DSL 与关键字帮助、诊断 | 编辑中、校验失败、保存成功；实际 lifecycle 以模型为准 |
| 对象浏览 | 数据列表、对象详情、关系与计算属性 | 加载、空数据、部分展开、查询拒绝 |
| 操作执行 | 参数、规则、风险、预演变化和执行结果 | 预演失败、可执行、等待确认、成功、拒绝或故障 |
| 待确认任务 | 发起者、责任人、对象前后值、影响范围 | 待裁决、批准、拒绝、执行前需重新预演 |
| 审计与治理 | 事件因果链、会话、漂移发现 | 业务结果、外部失败、扫描未完成与处理记录 |
| 平台管理 | 账户、密钥、角色、作用域及部署能力 | 授权范围、密钥状态与管理操作结果 |

业务界面使用可理解的对象名称、规则说明与处理建议。SQL、AST、指纹等技术信息可以用于诊断视图，不应成为普通业务操作必须理解的字段。

## 8. 贯穿业务场景：采购审批

本节是建议用于产品验收的业务场景，不表示平台预置采购模板或指定审批制度。

### 8.1 场景模型

| 元素 | 示例定义 | 验证的能力 |
| --- | --- | --- |
| 对象 | 采购订单、供应商、审批记录 | 对象身份、属性及数据源绑定 |
| 属性 | 金额、状态、审批人、审批时间 | 类型、可写性、展示和引用 |
| 关系 | 订单关联供应商与审批记录 | 关系命名、导航和基数 |
| 操作 | 提交订单、审批订单、批量审批 | 前置条件、写入、级联和批量 |
| 规则 | 订单须已提交、金额满足规则、状态迁移合法 | 同步约束和具体拒绝反馈 |
| Function | 依据参数或当前数据计算是否需人工复核 | 纯计算、只读计算及故障处理 |
| 接口 | 多类单据共享审批契约 | 查询多态与受控分派 |

### 8.2 建模者完成准备

建模者接入采购数据、确认主键和关系角色，定义审批 Action 与规则。使用 DSL 时，`require` 表达前置条件，`set` 表达状态写入，`create` 表达审批记录，`emit` 表达业务事件。保存前修正所有阻断诊断，再核实物理结构与模型一致。

### 8.3 人或 Agent 发起操作

执行者先读取订单和操作说明。系统按实际角色及数据范围判断资格，按自动化属性和风险决定直接执行或进入确认。预演展示订单前后状态和审批记录等影响，审批者裁决的是这些具体变化。

正式执行重新取得真实状态，运行 Function 与约束，按序写入，统一提交业务和成功事件。审计人员随后能看到执行者、责任人、使用的模型版本与变化因果链。

### 8.4 关键异常

| 触发条件 | 期望行为 |
| --- | --- |
| 订单仍为草稿 | 拒绝审批并提示先提交，订单与审批记录不变 |
| 执行者角色或数据范围不满足 | 权限拒绝，人工确认不能补足权限 |
| Function 超时或读取失败 | 作为计算故障阻断，不当作业务规则已经通过 |
| 预演后订单被他人修改 | 变更指纹不符时拒绝旧确认，重新预演 |
| 子操作触发阻断规则 | 整条审批链回滚 |
| 相同请求因网络重试再次到达 | 按幂等契约重放结果，不再创建审批记录 |
| 数据库提交后外部通知失败 | 审批保持已成功，单独展示通知失败 |
| 批量审批触及上限 | 拒绝超范围执行，提示缩小批次或检查调用模型 |

## 9. 交付验收清单

以下用例应在实际应用仓库连接数据库执行；本仓库只能检查需求表达与文档一致性。

| 用例 | 验收动作 | 通过条件 |
| --- | --- | --- |
| `AT-01` | 导入包含非法字段类型和缺失主键的接入草案 | 问题明确列出，未生成伪合法模型 |
| `AT-02` | 保存包含悬空引用或循环调用的模型 | 原子拒绝，定位实体和引用点 |
| `AT-03` | 编写引用未来步骤结果的 DSL | 作用域诊断明确，不进入执行 |
| `AT-04` | 将已保存 Action 格式化再解析 | 参数、角色、风险与自动化属性不变 |
| `AT-05` | 查询有空关联与多个子对象的分页数据 | 父对象分页与关系含义正确，限制可见 |
| `AT-06` | 预演一次包含创建和修改的操作 | 返回真实变化，业务、执行事件与幂等结果不提交 |
| `AT-07` | 在级联末端触发规则失败 | 根操作与子操作全部回滚 |
| `AT-08` | 同键并发或超时后重试成功业务请求 | 按实际契约避免重复生效并返回可解释结果 |
| `AT-09` | 用 pure／readonly Function 尝试越过能力边界 | pure 无查询能力，readonly 无业务写入能力 |
| `AT-10` | 运行故障、超时或不支持的 Function | 阻断依赖它的操作，显示计算故障 |
| `AT-11` | Agent 直接调用禁用自动化的 Action | 服务端拒绝，不依赖工具列表过滤 |
| `AT-12` | 人工批准后替换参数或改变目标数据 | 旧确认不能复用，正式执行不留部分结果 |
| `AT-13` | 通过接口调用同一业务操作 | 与具体对象调用具有一致权限及治理语义 |
| `AT-14` | 在事务提交后令外部服务调用失败 | 业务成功与外部失败被正确区分 |
| `AT-15` | 物理结构变化后施加旧迁移计划 | 指纹不符被拒绝，不施加旧计划 |
| `AT-16` | 扫描结构／约束漂移并中断扫描 | 发现、跳过及未完成范围准确可见 |
| `AT-17` | 从审批事件追踪责任与级联结果 | 身份、模型版本、对象变化与因果关系完整 |
| `AT-18` | 超出批量或级联护栏 | 不发生半条业务链，反馈指向合理处理者 |

## 10. 质量要求

- **一致性**：受支持的事务部署中，业务变更、成功事件和幂等结果必须共同提交；不得以跨库写入冒充原子事务。
- **可追责**：非人类操作能追溯到责任主体；确认内容与最终执行结果一致。
- **可解释**：未接入、未编译、未扫描及不支持的部分均有明确反馈。
- **可演进**：模型变更有版本，数据库迁移有计划与历史；破坏性迁移不自动执行。
- **性能与容量**：在目标环境测量查询延迟、操作延迟、并发量和订阅延迟后确定指标，不在本版承诺未经验证的数值。
- **资源边界**：查询展开、批次、级联与脚本计算受限，超限可终止并给出原因，不能长期占用连接或事务。
- **多入口一致性**：HTTP、MCP、工具和接口分派复用业务语义，不能因入口不同绕开规则。
- **可运维性**：模型缓存过期、事件可见性不足、拒绝留痕失败、外部调用失败及扫描未完成能够被识别并处理。

上线前应补充容量测试环境、数据规模、并发模型、延迟分位数、错误率与事件订阅积压的基准。审计保留、备份恢复和身份系统集成要求由部署方确认，不能仅凭逻辑分层作出可用性承诺。

## 11. 建议交付顺序与待确认项

以下为建议交付顺序，不对应笔记中的历史开发阶段，也不表示能力当前尚未实现。

| 阶段 | 交付重点 | 完成标准 |
| --- | --- | --- |
| 业务闭环 | 单一业务域的接入、建模、查询、操作与审计 | 采购审批示例可完整运行，合法与非法路径均可验收 |
| 协同治理 | Agent 工具、权限、预演、确认和会话 | 人与 Agent 执行同一业务时遵守相同规则，自动化风险受控 |
| 扩展演进 | 接口多态、模型演进、漂移治理及容量验证 | 新对象可复用公共契约，变更与数据问题可持续治理 |

后续需确认首个业务场景、建模与运维责任人、界面交付范围、身份系统集成、数据与审计存储拓扑，以及性能和保留周期目标。属性敏感度过滤、外部调用可靠投递和非 SQL 数据源接入须单独核实后进入交付承诺。

首轮交付应将建模与 DSL 诊断、查询、Action、Function 的受控计算及审计串成可验收业务链，再补齐复杂接口、更多连接方式和运营功能。功能优先级不等于实现状态；任何声明为可交付的能力，都应能对应上述用例与代码验证结果。
